## Protocol and exactness

The documented alternating three-pair protocol was chosen before the runs.
Each backend ran in a fresh sequential subprocess, with no workload warmup,
no affinity changes and no altered arithmetic. The five unit-test groups ran
first in a separate process and passed. The original manifest's 20 entries
were verified. A fresh venv installed the official released python-flint 0.9.0
wheel using the original hash-pinned requirement from PyPI. Its recorded digest
and URL are in `environment.json`; no root-isolation development build was used.

For **each of six runs**, the strict published comparator passed against the
preserved expected final jet and original reference receipt. For **each pair**,
it also passed reference versus FLINT. This checks all 361 integer midpoints,
the common integer radius and parameters, and all 21 nonperformance receipt
fields. Only `seconds` and `peak_rss_kib` are excluded from receipt equality.
All six final-jet files have the same SHA-256 as the preserved fixture:
`4dfdadc447233dd5b0ea5a4e3da10cf7c7f7e4c1e77ee43bddb9233bbdf2acb5`.
The six original receipts and output files are retained under `runs/`.

## Environment and limitations

CPython 3.12.14; Linux x86-64; reported AMD EPYC 9V74; 9 visible logical CPUs.
This was a shared cloud environment, **not an exclusive or controlled CPU**.
Other work could include brief symbolic checks and PDF rendering. Start/end
1-, 5-, and 15-minute load averages are included per run as diagnostics, not
as evidence of exclusive allocation. CPU quota files were unavailable; CPU
frequency, physical allocation, host contention and scheduling were uncontrolled.

Primary timings are the unchanged runner's internal wall-clock `seconds`,
including certificate generation, Horner evaluation and bound construction,
but excluding startup/import and final JSON writes. External whole-process
wall times and process-wide peak RSS are retained separately. Three pairs
are descriptive evidence, not a confidence interval or universal speed claim.
Do not compare these absolute times to another machine or interpret them as
a whole-proof ETA. Even similar reported CPU models do not establish comparable
allocation. FLINT/python-flint deserve the exact-arithmetic backend credit.
This benchmark validates the arithmetic substitution; it does not itself
establish or independently audit the mathematical theorem.

## Repeat the measured workload

From `benchmarks/exact-convolution`, after the README's hash-pinned installation:

```sh
python -m unittest -v test_exact
python run.py --backend reference --output results/repeat/pair1_reference
python run.py --backend flint --output results/repeat/pair1_flint
python run.py --backend flint --output results/repeat/pair2_flint
python run.py --backend reference --output results/repeat/pair2_reference
python run.py --backend reference --output results/repeat/pair3_reference
python run.py --backend flint --output results/repeat/pair3_flint
python repeat-results/2026-11-02/verify.py --runs results/repeat
```

Use empty output directories and keep assertions enabled. Allow roughly
15–20 minutes plus overhead; new measurements will vary. `verify.py` compares
each new output to the fixture and its pair; it does not claim new measurements
must equal these historical times. `raw_timings.json` and `summary.json` are
observed records, not regenerated by that comparison command.
